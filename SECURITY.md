# Security policy

Game Save is a small self-hosted program. It is built for **one household**, on
**a home network**, and this document says in plain words what it is built to
withstand and what it is not.

---

## 1. The scope, said out loud

**Game Save is not for commercial use.** It is not a hosted service, it has no
billing, no account system, no telemetry. There is no team behind it and there
is no support contract.

**It is made for a home network.** It is meant to be reachable from the
machines of one household: a PC, a laptop, a NAS, a Raspberry Pi.

**It is not built to resist an adversary.** If somebody can reach the port,
they are on the network, and the program does not try to survive a determined
attack. There is no rate limiting, no fail2ban, no account lockout. The API
key is the only thing standing between a stranger and the saves.

**It must never be exposed to the public internet.** Not even "just for a
while", not even behind a password page. An exposed instance is an open door to
the save files of everybody who uses it.

## 2. How to keep it private instead of exposing it

There are several ways to reach a home server from outside without opening a
port. **Use one of these. Not the port.**

### Tailscale, or a similar mesh VPN

The simplest. Every machine joins the same tailnet, the server listens on its
Tailscale address, and nothing is exposed to the internet. Works from a phone,
a laptop, a work PC.

```text
server:   https://gamesave-machine:8443
```

### WireGuard

One interface, one peer per device, all traffic goes through the tunnel. Works
everywhere, needs a public endpoint for the gateway (or a small VPS, or a
machine at home with a public IP and port forwarding — **only the WireGuard
port**, not the Game Save port).

### ZeroTier, Nebula, OpenVPN

Same idea, different tools. Pick the one you already know.

### A reverse SSH tunnel

If the server is at home and you only need it from your laptop:

```bash
ssh -N -R 8443:localhost:8443 user@home
```

### A reverse proxy with a real certificate

If you already have a domain and a proxy (Caddy, nginx, Traefik), the proxy can
terminate TLS with a certificate from Let's Encrypt. This is **still exposing
the service to the internet**, so the proxy must require authentication in
front of it and the API key must be strong. Prefer the options above.

### The things that do not count

- **Port forwarding on the router**, alone. Exposing the port is exposing it.
- **A firewall rule that allows only some IP addresses**, unless those
  addresses are yours and static. IPs can be spoofed and your phone changes IP
  every day.
- **"Nobody will find it on port 8443."** Scanners sweep the whole IPv4 space
  in minutes.

## 3. What the server protects, and how

- **The transport**: a certificate authority generated by the server itself,
  signed by it. The client pins the fingerprint of that authority and refuses
  anything else. This is why the client asks for the fingerprint once: without
  it, an attacker who can sit between the client and the server can present
  their own certificate.
- **The API keys**: stored as a SHA-256 hash, shown once at creation, revocable
  at any time. One key per machine.
- **The accounts**: each account sees only its own games and files.
- **The files**: stored on disk, content addressed, with the history of every
  version.

What it does **not** do: encrypt the files at rest, check that the client is
who it says beyond the API key, protect against a compromised machine.

## 4. Reporting a vulnerability

**Do not open a public issue.** A public issue advertises the problem to
everybody before it is fixed.

Write privately. The maintainers of the repository will answer.

Say, at least:

- what can be done (the effect, not only the cause);
- how to reproduce it;
- whether it needs an account, or a machine on the network;
- whether you have already shared it somewhere else.

The maintainers will acknowledge the report, tell what they intend to do, and
ask for a reasonable delay before any public disclosure. A month is reasonable;
the project is small and the maintainers have jobs.

## 5. Supported versions

| Version | Supported |
|---|---|
| 0.1.x | yes |
| anything older | no |

The project has no stable API yet. The server and the client must run the same
version; a client of a different version may refuse to connect, and that is
correct.

## 6. Known limitations

Say them before somebody else finds them:

- **The files are not encrypted at rest.** Somebody with access to the data
  directory reads the saves. The end to end encryption is planned, opt-in, and
  not here yet.
- **A user who can write to the data directory can write to the database.** The
  server does not defend against that; the operating system is supposed to.
- **The API key travels in a header.** On a LAN, that is fine. Over the
  internet, it is the tunnel that protects it, not the program.
- **There is no audit log.** A revoked key stops working, and that is recorded
  only in the last-used time of the key.
- **The certificate is valid for ten years.** Long, because a homelab should
  not have to renew things. The fingerprint is what the client checks, so a
  renewal is a change of fingerprint and the client will say so.

## 7. A checklist before turning it on

- [ ] the server listens on the LAN, not on `0.0.0.0` exposed to the internet
- [ ] the port is not forwarded on the router
- [ ] the data directory is owned by the user that runs the server, and not
      readable by others
- [ ] the fingerprint of the certificate authority is pinned in every client
- [ ] there is a key per machine, and the keys you do not use are revoked
- [ ] the backup of the data directory exists and is somewhere else
